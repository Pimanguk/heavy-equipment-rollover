## 3. 데이터·계산에서 달라지는 점 (중요)

### 3-1. 부품 질량: 팀 시트 02 ≠ CAT 공식 무게표

| 부품 | 팀 시트 02 | CAT 공식 무게표 | 차이 |
|---|---|---|---|
| 버킷 | 1,200 kg | 880 kg | +36% |
| 암 | 1,800 kg | 1,300 kg | +38% |
| 붐 | 3,300 kg | 2,050 kg (붐 1,710 + 실린더 340) | +61% |
| 회전몸체 | 12,300 kg | 10,610 kg (합계 맞춤 보정) | +16% |
| **하부 주행체** | **4,000 kg** | **7,760 kg** (프레임 4,390 + 슈 3,370) | **−48%** |
| 합계 | 22,600 kg | 22,600 kg | 같음 |

**판정에 주는 영향** (팀원 시뮬레이터 안에서 질량만 바꿔 측정, 평지):

| 자세 | 팀 시트 | CAT 공식 |
|---|---|---|
| 초기 자세 | 여유 +0.95 m, 무게중심 높이 1.94 m | +1.03 m, 1.63 m |
| **옆으로 길게 뻗음** (붐 10°, 암 −20°, 선회 90°) | **+0.11 m (전복 직전)** | **+0.54 m** |
| 앞으로 길게 뻗음 | +0.82 m | +1.03 m |

→ 무거운 하부가 가볍게, 앞쪽 작업장치가 무겁게 잡혀 **무게중심이 높고 앞으로 쏠림**. 옆으로 뻗을 때 여유가 5배 가까이 차이.
→ 인양 능력표 확인(정확도 검증)은 CAT 공식 구성 기준이므로, **검증과 같은 질량을 써야 숫자가 맞는다.**
→ 팀 시트 02의 출처가 확인되지 않음. **결정 필요(5절).** 웹에서 두 질량표를 전환할 수 있게 넣는 중.

### 3-2. 무게중심 위치 산정
- 팀원 방식: 각 부품 **바운딩박스 중심**을 무게중심으로 사용.
- 문제: 회전몸체는 카운터웨이트 때문에 실제 무게중심이 뒤쪽에 있는데(조사 추정 선회축 뒤 약 1.45 m), 박스 중심은 이를 반영하지 못함. 팀원 정리표의 "후방 무게중심 오프셋 반영"이 코드에는 아직 없음.
- 초기 자세에서 무게중심이 옆으로 0.23 m 치우쳐 나옴(모델 비대칭 또는 박스 중심 영향). 확인 필요.
- 조치: 부품별 무게중심 오프셋을 상수로 두고, 인양표 6.0 m 열로 보정 → 나머지 칸으로 검증(기획서 3.3절 절차 그대로).

## 4. 기획서(PLAN.md)에서 바뀌는 항목

- **D3(렌더러)**: 결정 완료 → three.js. 1일차 오전 "Cloud 배포 스파이크"는 불필요.
- **모듈 구조**: Python `kinematics.py / terrain.py / render` 분리안 대신, 웹 한 파일(`index.html`)에 기능을 덧붙이고 `physics.py`는 검증 기준으로 남긴다.
- **역할**: C1(three.js 렌더) 일은 팀원 결과물 위에서 경사·카메라·배경을 붙이는 일로 줄어듦. R1·R2는 판정식(경사·요철·6점 접지)과 인양표 검증에 집중.
- **오프라인 데모 위험**: three.js를 CDN(jsDelivr)에서 받음 → 인터넷이 없으면 화면이 안 뜸. 발표 전 three.js 파일을 `web/`에 넣어 로컬로 바꿀 것.
- **Streamlit 앱**: 레거시로 동결. 배포 URL은 웹 시뮬레이터로 교체 예정.
